# PLATFORM_PLAN.md — Пользователи, организации, пакеты, права

> Статус: **DESIGN / ROADMAP**. Это план, а не описание существующего кода.
> Ветка реализации: `feature/platform-packages-tenancy`.
> Цель документа — зафиксировать целостную картину для четырёх переплетённых
> фич (пакеты, организации, пользователи, права), последовательность их
> внедрения и список архитектурных рисков, прежде чем писать код.

## 0. Резюме для занятых

Четыре фичи связаны, но **разделяемы**. Рекомендуемый порядок:

1. **Пакеты** (самая автономная, начинаем с неё) — реестр + publish/install +
   round-trip экспорт + версии пакетов поверх существующих веток графа +
   расщепление канала распространения impl/не-impl.
2. **Тенантность / организации** — `org-id` по образцу `branch-id`, два слоя
   изоляции (app-decorator + Postgres RLS), поддомены и кастомные домены.
3. **Пользователи и права** — модель пользователя вместо общего пароля +
   минимальный примитив `grant(subject, capability, ns-scope)`.
4. **Распил монолита** (будущее) — через протоколы + deps.edn git-deps, НЕ через
   Polylith как обязательное условие.

**Главный вывод, меняющий рамку всей задачи:** граница безопасности облака —
это **НЕ «пакеты без impl»**, а **гейтинг эффектов в рантайме executor'а**,
которого сегодня нет (см. §1 и риск R1). «Пакеты без impl» — условие
необходимое, но недостаточное.

**Второй вывод, упрощающий модель:** оси не три («облако / self-hosted /
смешанный»), а **две независимые**: где живёт граф и где крутится executor.
Смешанный режим тогда раскладывается в уже понятные части (см. §1).

**Третий вывод (ADR §3.0), задающий форму фаз 2–3:** организации/юзеры/права
и их энфорсмент — это **опциональный Integrant-аддон** (impl-канал, deps.edn),
а не граф-пакет (границу безопасности нельзя реализовать тем, что она
ограничивает) и не форк. Система работает с аддоном (мультитенант) и без него
(single-tenant). «Облако» = тот же бинарник + аддон + restriction-политика +
admin-доступ за VPN. Продукт организаций (UI/админка) — fns-пакет поверх аддона.

**Статус:** фаза 1 (пакеты: экспортёр + реестр publish/install) и фаза 1.5
(механизм гейта эффектов + аудит) — **сделаны** (см. §8). Фазы 2–3 = постройка
tenancy-аддона, фиксируется этим документом.

## 1. Три типа пользователей → две оси

Вместо трёх «типов» удобнее думать о матрице 2×2:

|                          | Executor: наш                     | Executor: пользователя             |
| ------------------------ | --------------------------------- | ---------------------------------- |
| **Граф (fn-строки): наш**| **Облачный** (тип 1)              | **Смешанный** (тип 3)              |
| **Граф: пользователя**   | (нет смысла — пропускаем)         | **Self-hosted** (тип 2)            |

Что это даёт:

- **Облако:** весь impl — *наш* код. Пользователь никогда не присылает Clojure.
  Но он **компонует существующие base-fn**, часть которых выполняет эффекты
  (`:env`, `:read-resource`, сетевые, `:pg-query`). Значит безопасность ≠
  «нет impl», а «executor не даёт выполнить запрещённый эффект» → **гейтинг
  эффектов** (R1).
- **Self-hosted:** executor — *их*. Любой impl — их ответственность. Наша
  поверхность — ноль.
- **Смешанный** = *наш storage API (со скоупом по ключу организации)* +
  *их executor (self-hosted-стиль)*. То есть смешанный режим **не новая
  сущность**, а композиция: «org-scoped storage API» (фаза 2) + «их executor»
  (фаза 4). Гейтинг эффектов в смешанном — их забота, не наша; наша забота —
  чтобы storage API **никогда** не отдал чужие данные даже при баге (→ RLS).

Вывод: смешанный режим **реализуем** и почти бесплатен, если фазы 2 и 4 сделаны
правильно. Отдельного кода под него почти не нужно.

## 2. ФАЗА 1 — Пакеты

### 2.1. Два канала распространения (ключевое разделение)

| Канал                       | Что распространяет                                  | Механизм                              | Кто может ставить в облаке |
| --------------------------- | --------------------------------------------------- | ------------------------------------- | -------------------------- |
| **Impl-канал**              | пакеты с `impls.clj` (Clojure-код, новые примитивы) | git-репозиторий / Maven (deps.edn)    | **никто** (это код на нашем executor) |
| **Fns-канал**               | пакеты только с `fns.edn` (композиции над impl)     | наш реестр, EDN по HTTP → строки графа| **да** (это данные, не код), при условии гейтинга эффектов |

Почему так:

- impl-пакет = новый Clojure-код → может выполнить что угодно на executor'е,
  где он скомпилирован. В облаке его собираем **только мы**, и делаем доступным
  всем. Self-hosted/смешанный пользователь добавляет его в **свой** executor.
- fns-пакет = только описание композиций (строки `fn/slot/binding`). Установка =
  sync EDN в граф. Никакого выполнения кода. Поэтому облачный пользователь может
  ставить fns-пакеты сам — но что он может ими *делать*, ограничивает гейтинг
  эффектов (R1), а не факт наличия impl.

Любой fns-пакет транзитивно зависит хотя бы от одного impl-пакета (у любой fn
самый древний предок — base-fn с impl). Это становится **объявленной
зависимостью пакета** (см. 2.3).

### 2.2. Распространение impl-пакетов: deps.edn git-deps, НЕ Polylith, НЕ submodules

Рекомендация (ответ на вопрос про Polylith):

- **Распространение impl-пакетов** — нативный механизм Clojure: каждый impl-пакет
  это свой git-репозиторий с `package.edn` + `impls.clj` + `deps.edn`.
  Self-hosted пользователь добавляет git/Maven-координату. Это и есть «обычные
  git-репозитории и clojure-библиотеки», как ты и предполагал.
- **Автоматизация «добавил в одном месте — сборка подхватила»**: вводим
  манифест `executor-packages.edn` (список координат пакетов). Шаг сборки
  (`build.clj`) сплайсит его в `deps.edn` `:deps`/`:extra-deps` и в список
  загружаемых пакетов loader'а. Пользователь правит **один файл данных**, не
  трогая код executor'а → меньше шанс случайно сломать executor. Ровно та
  автоматизация, которую ты хотел.
- **Polylith** — это инструмент организации монорепы (components/bases/projects).
  Он *помог бы* структурировать наши компоненты, но **не требуется** для
  swappability: кодовая база уже протокол-ориентирована (`StorageCRUD`,
  `ExecutionGraph`, `data-schema-protocol`, integrant). Swappability даёт
  протокол + integrant, а не Polylith. Вердикт: **Polylith — приятно потом,
  не блокер сейчас.** Не закладываемся.
- **Git submodules** — не использовать. deps.edn git-deps — clojure-нативный
  эквивалент, без боли submodule'ов.

### 2.3. Версии и зависимости пакетов

Сегодня (проверено): `package.edn` имеет `:dependencies ["core" ...]` — голые
имена без версий; топосортировка зависимостей уже есть; `:version` — чистая
метадата, в рантайме не используется; `impl-hash` — заглушка `nil`.

Что добавляем:

- **Версионные констрейнты** в `:dependencies`: `{"core" ">=1.5.0"}`.
  `resolve-dependencies` (loader.clj) проверяет и тянет из реестра.
- **Реальный `impl-hash`** (SHA-256 канонической формы impl) — нужен для
  детекции breaking-change при смене версии impl-пакета (R4). Сейчас всегда nil.
- **Проверка при установке**: нельзя поставить fns-пакет, чьи узлы ссылаются на
  отсутствующих предков. resolver проверяет наличие пакетов-зависимостей в
  целевой системе и при необходимости тянет и ставит их (рекурсивно).

### 2.4. Три системы версий и как они соотносятся

| Система                         | Что версионирует            | Существует? |
| ------------------------------- | --------------------------- | ----------- |
| **Ветки графа** (git-подобные)  | per-entity версии fn-строк  | да          |
| **Версии пакетов** (semver)     | снимок EDN-бандла           | метадата    |
| **Версии git-репо** (impl)      | git-тег / Maven-версия      | стандарт    |

**Главная синергия (важно):** «проверить новую версию пакета на тестовой ветке
перед продом» = **поставить новую версию пакета на ветку графа**, прогнать тесты,
затем смержить в `main`. Откат = revert merge или переустановка старой версии.
То есть существующая система веток графа **уже является** стейджингом для
апгрейда пакетов. Ничего нового изобретать не надо — переиспользуем ветки.

- Импорт версии «из dev/другой ветки» = установка на соответствующую ветку графа.
- Уведомления о новых версиях = реестр хранит latest; периодическая сверка
  installed-version vs registry-latest по организации.
- «У пакета может измениться только impl» → это про impl-канал: новая версия
  Maven/git-координаты, ловится по `impl-hash`-дрифту.

### 2.5. Реестр (PyPI-подобный) и публикация

- **Реестр fns-пакетов** — сервис: пакет = именованный версионированный бандл
  `fns.edn` (+ вложенные неймспейсы как структура папок). Публичный или
  доступный по ключу организации. Просмотр описаний/версий — как pypi.org.
- **Публикация облачным пользователем БЕЗ создания файла руками**: API
  `POST /api/packages/publish` принимает корневой неймспейс → сервер
  **сериализует поддерево графа в EDN** (см. 2.6) → сохраняет как версию пакета.
  Пользователь не возится с git/файлами.
- **Публикация self-hosted пользователем независимо от нашего реестра**: тот же
  экспортёр выдаёт `fns.edn` (или набор с папками для вложенных ns) → пользователь
  кладёт в свой git. Реестр — опционален.

### 2.6. Round-trip экспортёр `граф → fns.edn` (отсутствует, нужен)

Сегодня (проверено): сериализации графа обратно в EDN **нет вообще** — система
односторонняя (EDN → строки). И publish, и export требуют этого. Это
**фундаментальная подзадача фазы 1**: обратный проход к парсеру `records`
(`fn/slot/fn-slot/binding/binding-list-item` → `fns.edn`-формы). Хорошо
ограничена по объёму.

### 2.7. Пакеты ↔ неймспейсы (с учётом реальной схемы)

**Поправка к твоему вопросу:** в текущей схеме связь fn↔namespace —
**один-к-одному** (`fn.namespace-id` — единственный FK), а `:ns` — дерево
(`parent-id`). M2M, который ты помнишь («одна fn в разных неймспейсах»), в
схеме **не реализован** (см. R-NS). Поэтому неоднозначности «к какому неймспейсу
относить при упаковке» сегодня нет.

Модель:

- **Пакет = именованный версионированный экспорт поддерева неймспейса** (один
  корневой ns + его дочерние). Замыкание fn под корнем + их зависимости из
  других неймспейсов → становятся **объявленными зависимостями пакета**.
- Если/когда m2m для неймспейсов появится (для твоего interface-gathering
  кейса — «собрать все места, где нужны секреты»), то такой **сборочный
  неймспейс-вид — НЕ пакет**, а представление (view). Паковать его смысла нет
  (ты сам это и заметил). Для упаковки нужно понятие «домашний неймспейс»
  (primary membership); вторичные membership в пакет не входят.

### 2.8. «Установка» для облака = грант видимости, а не дублирование строк

Облачный пользователь **не должен** дублировать у себя файлы/строки публичного
пакета. Поэтому:

- Публичные fns-пакеты живут один раз в **public-организации** (общий тенант).
- «Установка пакета» облачным пользователем = **грант на чтение** неймспейса
  этого пакета в его **workspace** (см. фазу 3, §4.4). Строки не копируются.
- Это прямо отвечает на твою догадку: «установка пакета связана с настройкой
  видимости неймспейсов». Пакеты, workspaces и права **унифицируются через
  ns-scoped гранты**.
- Форк/модификация публичного пакета = copy-on-write в свой неймспейс (тогда
  строки копируются, но только при намеренном форке).

### 2.9. Что вынести из текущего репозитория

После появления системы пакетов в ядре оставляем **минимально необходимое**:
executor, storage, versioning, packages-loader, web-примитивы, server-скелет,
ядро base-fn. Кандидаты на вынос в отдельные репозитории/пакеты:
доменные/примерные пакеты, нестандартные impl-пакеты, возможно сам editor
(это продукт, но технически — app-пакет). Цель — уменьшить объём и шум ядра.

## 3. ФАЗА 2 — Организации и тенантность

### 3.0. ADR: tenancy = опциональный Integrant-аддон, НЕ форк и НЕ граф-пакет

**Решение.** Организации, пользователи, права и весь их **энфорсмент**
оформляются как **опциональный impl-аддон** (Clojure-зависимость, deps.edn
git-dep — это impl-канал из §2.1), подключаемый через Integrant. Система
работает **с аддоном и без него**: без него — single-tenant (один неявный
org `public`, `:allowed-effects nil`, auth = текущий single-token); с ним —
мультитенант + effect-gate + права. Продуктовая часть (админка организаций,
управление юзерами, UI грантов, workspace-вид) — **fns-пакет поверх аддона**.

**Почему именно так (а не граф-пакет и не форк).** Граница безопасности не
может быть реализована тем, что она ограничивает: user-граф исполняется
*внутри* executor'а, и если бы изоляция/гейт сами были граф-пакетом —
композицией их можно обойти. Значит энфорсмент обязан жить ниже графа, в
ядре. Но он не должен ни форкать «cloud vs self-hosted», ни раздувать базовый
бинарник. **Опциональный core-level аддон** снимает оба: один код, разница —
наличие зависимости в конфиге. Это переиспользует уже имеющиеся кости
graphden — декораторы storage (`VersionedStorage` уже такой), Integrant,
`extend-builder` (так добавлена `:package-version`), двухканальную модель
пакетов — то есть архитектурно «бесплатно».

**Что в аддоне (impl), что в core, что в графе:**

| Слой | Где | Почему |
|------|-----|--------|
| `OrgScopedStorage`-декоратор (org-фильтр) | **аддон** (impl) | оборачивает storage-цепочку: `OrgScoped(Versioned(Postgres))` |
| Postgres RLS (`SET LOCAL app.current_org`) | **аддон** (DB-политики) | нижний предохранитель — если app-код «вынырнул», БД режет чужие строки |
| auth-middleware (session/JWT → org/user) | **аддон** (impl) | переопределяет core-шов auth |
| `extend-builder`: `org`/`user`/`grant` | **аддон** (impl) | расширяет схему как `pkgs/extend-builder` |
| Установка `:allowed-effects` на per-request ctx | **аддон** (impl) | механизм гейта уже в core (§5); аддон ставит политику |
| Host→org резолвер | **аддон** (impl) | расширяет `branch_router/dispatch` |
| `org-id`-колонка (default `public`) | **core** | cross-cutting поле; аддон лишь включает scoping (см. нюанс 2) |
| Механизм гейта (`record-effect!` throws) | **core** (готово) | граница не может быть аддоном, который её снимает |
| Примитив `grant` + проверка на request-boundary | **core** | энфорсмент не композируем юзером |
| Продукт: админка org, управление юзерами, UI грантов | **граф (fns-пакет)** | это композиции → им место в пакете; зависят от сущностей аддона |

**Cloud vs self-hosted = режим, не код.** Один бинарник. «Облако» = аддон
подключён + restriction-политика (org-юзерам запрещены `:env`/`:io`/
`:network`/`:process`, недоступны impl-пакеты) + platform-admin доступ за VPN
(мы оперируем облаком как self-hosted-админ). Минимальный self-hosted = без
аддона, single-tenant. Self-hoster, которому нужен мультиюзер, **тоже ставит
аддон** — он не «облачный».

**5 нюансов/предусловий (по убыванию важности):**

1. **Декоратор обязан быть непробиваемым.** В коде есть `vs/unwrap`
   (branch-router достаёт базовый storage) — любой такой путь мимо
   `OrgScopedStorage` = дыра в изоляции. Поэтому RLS обязателен как второй
   слой (даже если app-код вынырнул, БД режет). RLS-политики — schema
   аддона → подключение/отключение = миграция.
2. **`org-id` — core-колонка (default `public`), а не «появляется с
   аддоном».** Чтобы core-запросы работали в обоих режимах. «Полностью
   опциональное» слегка размывается на уровне данных: колонка есть всегда,
   энфорсмент включает аддон. Это легитимное cross-cutting поле (ADR R5).
3. **Механизм инъекции в Integrant.** Конфиг — статическая EDN-карта; нужен
   манифест аддонов (аналог `executor-packages.edn` из §2.2), который boot
   читает и **сплайсит Integrant-ключи аддона** в storage/router-цепочку,
   не хардкодя их в core-конфиге.
4. **Auth сначала вынести в сменный шов.** Сегодня auth — хардкод одного
   токена. Чтобы аддон его *заменял*, core нужен auth как инъектируемый
   компонент (протокол/Integrant-ключ). **Предусловие №1** — без него
   остальное не подключить чисто.
5. **Зависимость продукта от аддона.** Граф-пакет «org-admin» ссылается на
   сущности `org`/`user` → транзитивная зависимость fns→impl (§2.1);
   проверяется при install (уже реализовано для install в фазе 1).

**Порядок реализации (уточняет §8):** auth-шов (предусловие) → манифест
аддонов (механизм инъекции) → `OrgScopedStorage` + RLS (изоляция, оба слоя)
→ проводка effect-gate (аддон ставит `:allowed-effects`) → продуктовый
fns-пакет (org-admin UI). До auth-шва и манифеста — остальное не вклинить.

### 3.1. Изоляция данных: `org-id` по образцу `branch-id`, два слоя

Существующий `branch-id` — точный аналог тенант-скоупа (проверено:
`VersionedStorage` оборачивает storage и автофильтрует по `branch-id`).
Зеркалим его:

- **Слой A (app): `OrgScopedStorage`-декоратор** (как `VersionedStorage`) —
  инжектит фильтр `org-id` в каждый запрос. Эргономика и перф.
- **Слой B (БД): Postgres RLS** — `SET LOCAL app.current_org = ?` в начале
  каждой транзакции (HikariCP пулит коннекты, поэтому именно `SET LOCAL`
  внутри транзакции / `set_config(...,true)`, а не session-level onConnect).
  Это **жёсткая гарантия «даже если в нашем коде баг»**, которую ты и хочешь.

**Делаем оба.** RLS — нижний предохранитель (см. R6: сегодня чтение полностью
анонимно, поверхность огромна, app-слой что-то да пропустит). Org-id ставим
колонкой на `fn` и версионные таблицы; для публичных пакетов — спец-организация
`public`. Это **в напряжении с принципом #2** (минимум полей) — нужен явный ADR
(R5): тенант — легитимное сквозное поле, не семантика графа.

**Точка подключения effect-gate (см. §5):** per-org `ExecutionContext` —
это и есть restricted-ctx для гейта эффектов. При создании org-ctx для
user-graph исполнения: `(create-context {:storage org-storage :allowed-effects
compile-runtime/default-cloud-allowed-effects})`. Platform-ctx остаётся
unrestricted. Механизм гейта уже готов и проверен (Phase 1.5) — здесь только
прокинуть значение.

### 3.2. Поддомены организаций и кастомные домены (Heroku-стиль)

Сегодня (проверено): `Host`-заголовок не инспектируется; роутинг по веткам идёт
через `X-Graphden-Branch` / `?branch=`. Шов — `branch_router/dispatch` +
`extract-branch-ref`.

- **Авто-поддомен при регистрации организации**: `<org>.graphden.app` → тенант
  организации. Расширяем извлечение контекста: парсим поддомен из `Host` →
  резолвим в `org-id` (таблица `subdomain → org`). Маршрут создаётся
  автоматически при создании организации.
  - **resolution ✅** `tenancy.subdomain` — `extract-subdomain` (Host →
    label; strips port, rejects apex/multi-level) + `OrgResolver` протокол.
    **Дефолт — `identity-org-resolver`: label поддомена И ЕСТЬ org-id, НИКАКОЙ
    таблицы** (org — строка-слаг; неизвестный slug → пустой tenant-view через
    OrgScoped, валидировать нечего). `static-org-resolver` (map) — ТОЛЬКО для
    vanity-алиасов (subdomain ≠ org-id). **SECURITY: токен — авторитет org
    (single-membership), поддомен — ГВАРД, не источник.** Member на чужом
    поддомене → 403; поддомен НЕ расширяет доступ (спуф `Host` не прочитает
    чужую org, т.к. reads не grant-gated и OrgScoped скоупит по `*current-org*`);
    анонимус → public. `:tenancy/org-resolver` init-key (по умолчанию identity;
    `:subdomains` для алиасов) + `:base-domain`. Inert без резолвера. Доказано
    (5 тестов / 29 ассертов, вкл. cross-org 403 + anonymous-no-leak).
    *Остаётся:* авто-создание org при первом заходе на её
    поддомен (если нужно); таблица — только для **кастомных доменов** (R10,
    `hostname → org`, не выводится из org) + DNS-TXT.
- **Кастомные домены**: таблица `hostname → org`. Пользователь добавляет домен;
  **подтверждение владения** — DNS TXT-запись, которую мы один раз проверяем.
  - **✅ построено** `tenancy.domain`: `HostResolver` + `static-host-resolver`
    (`{hostname org}` верифицированных доменов) → `org-from-request`; wired в
    request-scope ПОСЛЕ поддомена, **та же guard-семантика** (токен — авторитет,
    host только запрещает). `verify-domain-ownership` (DNS-TXT
    `graphden-verify=<token>`, injectable lookup + JNDI default) — проверка
    владения. Доказано (3 теста, вкл. verify + member→org + foreign→403 +
    anon→public). *Остаётся:* storage-backed `hostname → org` + provisioning-
    флоу (добавить домен → выдать токен → verify → записать строку).
- **Важно (R10):** проверка DNS — это сетевой **эффект**, который облачным
  пользователям запрещён. Значит fn проверки домена — **привилегированная
  платформенная fn**, а не пользовательская композиция. «Через граф, но не
  пользователем» — тонкость, ломающая наивное «желательно через граф».
  **✅ соблюдено:** `verify-domain-ownership` — обычная Clojure-fn в аддоне
  (платформенная), НЕ граф-fn; тенант к ней не доберётся.
- **Важно (R11):** различаем два роутинга — (а) поддомен организации → тенант
  (editor/API) и (б) hostname развёрнутого пользователем веб-сервера → его
  `:service`. Это **разные** отображения, нельзя схлопывать в одно.

### 3.3. Пользовательские веб-серверы на поддомене (уже почти готово)

Сервисная модель уже умеет per-branch (проверено: `:service.branch-id` +
per-branch `ExecutionContext`, reconciler). Пользователь делает fn-def
`:parent :http-server` со своим `:handler`, заводит `:service` со своим
скоупом; reconciler поднимает его в нужном контексте; роутер направляет
запросы с подходящим hostname в этот сервис. Per-tenant runtime-config
(порт/путь) изолируется через уже существующий `:branch-local?`.

**Конкретный баг-риск (R8):** LRU-кэш per-branch хендлеров (`max 16`) должен
стать **per-org**, иначе ветки/хендлеры протекают между организациями.

**🔴 SANDBOX-предусловие (найдено + закрыт временный риск):** `:http-server`-
сервис биндит СВОЙ порт, его хендлер исполняется в ctx реконсилера, где НЕТ
`:allowed-effects` → tenant-задеплоенный сервис исполнялся бы **вне effect-
gate** (env/io/network/process), обходя весь облачный сэндбокс. Плюс `:service`
не org-scoped, а per-namespace write-guard пропускал не-`:fn`. То есть тенант с
любым write-грантом мог `POST /api/entities/service` и развернуть
несэндбокснутый веб-сервер. **Закрыто (storage-слой):**
`tenant-forbidden-entities #{:service :grant :domain :branch}` в
OrgScopedStorage — тенант (org ≠ public) не может ни писать, ни читать
привилегированные сущности (`:service` → escape, `:grant` → эскалация/
enumeration authz, `:domain` → hijack роутинга, `:branch` → не org-scoped:
tenant-ветка глобальна + пикер `/api/branches` перечислил бы ветки ВСЕХ org →
тенанты заперты на `main`); платформа (public) — свободно. authz не ломается,
т.к. grant-store читает `:grant` из БАЗОВОГО storage, не из декоратора;
branch-резолюция читает `:branch` в public-контексте (до request-scope), так
что гвард её не трогает. (Read `:execution` — отдельно, защищён неугадываемым
`fn-id`, низкая severity. **Прямой stamp НЕ годится:** executions пишутся в
background-future, где `*current-org*` (thread-local) не связан — OrgScoped
mis-tag'нул бы строку И own-guard ЗАБЛОКИРОВАЛ бы terminal UPDATE из future,
теряя результат тенанта. Нужен capture org в request-time + проброс в future,
не stamp — §3.3 follow-up.) Доказано (storage-test, 9 тестов). *Полное
решение §3.3 — сэндбокс для tenant-OWNED сервисов (org на `:service` +
`:allowed-effects` в ctx реконсилера для tenant-сервиса) — обязательно ДО того,
как деплой сервисов станет tenant-доступным.*

### 3.4. ADR: tenant-приложения = FaaS (handler-only), НЕ PaaS (свой сервер)

**Решение (заменяет подход «service-sandbox» из §3.3-note).** Облачный
тенант НЕ владеет `:service`/веб-сервером (Heroku-модель). Вместо этого —
**FaaS / Cloudflare-Workers-модель**: платформа владеет web-server'ами
(порты, кол-во инстансов, скейл, роутинг org→инстанс) — всё в графах,
СКРЫТЫХ от тенанта; тенант даёт ТОЛЬКО **handler-функцию** (request→response,
с внутренним path-роутингом). Для Graphden это родная модель: «код = граф
функций», значит «приложение тенанта = функция, платформа её вызывает».

**Почему лучше service-sandbox.** В PaaS-варианте тенант-`:service` биндит
свой порт МИМО request-scope → надо изобретать `:service-scope` seam +
per-request wrap через port/async-границу. В FaaS handler тенанта
исполняется ВНУТРИ уже-сэндбокснутого request-пути платформы → effect-gate +
org-scoping применяются автоматически. Самая сложная часть исчезает. Плюс:
#2 минимум сущностей (тенант редактирует одно `:binding`, не создаёт
`:service`), #3 explicit (один рычаг — handler; порты/инстансы — решения
платформы).

**Механика.**
- **`:org`-сущность** (orgs-реестр, платформенная, tenant-forbidden):
  `name` (= slug = поддомен = `*current-org*`), `handler-fn-id`, метаданные.
  Endpoint регистрации (платформенный граф) создаёт строку + поддомен.
- **Handler-слот:** per-org provisioned «locked» fn (нельзя удалить/
  наследовать, можно только редактировать handler-binding) ИЛИ общая fn с
  org-scoped binding'ом (тогда уникальность binding → `(fn,slot,org)`).
  Вариант с per-org locked-fn чище. «Locked» выражается грантом: capability
  только на этот слот, не на структуру fn.
- **Два роутинга (резолвит R11):**
  - **App** (handler тенанта, публичные посетители) → контекст org =
    **поддомен/домен** (аноним OK). Безопасно: handler X — сам гейткипер,
    OrgScoped не пускает его за данные X. Within-org exposure — отв-ть app.
  - **Editor/API** (`/api/*`,`/partials/*`) → авторитет org = **токен**
    (guard §3.2: чужой поддомен → 403).
- **Web-server скрыт:** `:http-server`/`:service` — platform-only (уже
  enforced write-deny). Порт — не фикс-литерал, а из функции (платформа
  решает кол-во/инстансы).
- **Кастомные домены** — тем же app-routing'ом: верифицированный
  `hostname → org` (`tenancy.domain`, DNS-TXT уже есть) → handler org.

**Предусловия/тонкости (честно):**
- **R8 (per-org compiled-handler кэш)** из «scale-оптимизации» становится
  **перформанс-предусловием** — иначе компиляция handler'а на каждый запрос.
- **Resource-лимиты** (timeout/memory на tenant-handler) — effect-gate не
  ограничивает CPU/память (noisy neighbor; верно для любой shared-модели).
- App-путь должен биндить `*allowed-effects*` для tenant-handler (та же
  механика, что в request-scope).

**Bounded-шаги (план реализации):**
1. `:org`-сущность + схема (`tenancy/org_schema`), tenant-forbidden, addon-wiring. ← ТЕКУЩИЙ
2. Endpoint регистрации org (платформенный fn-def: создать `:org` + вывести поддомен).
3. App-routing шов: отделить app-запрос (поддомен→org-контекст, аноним) от editor/API (токен).
4. Handler-слот: provisioning per-org locked `app-handler` + резолв `handler-fn-id` из `:org`.
5. Связать app-routing → исполнять handler org-scoped + effect-gated.
6. R8 per-org handler-кэш (перф).
7. Resource-лимиты (timeout/memory).
8. Кастомные домены в app-routing (host→org уже есть).

## 4. ФАЗА 3 — Пользователи и права

### 4.1. Аутентификация: заменить общий пароль

Сегодня (проверено): единственный `AUTH_TOKEN` (env) как bearer в localStorage,
никакой модели пользователя; **чтение вообще анонимно**; секреты — все видят все.
Это полная переделка auth: таблица `user`, сессии/JWT, извлечение
user-контекста в middleware (`ring-adapter`), проброс в `ExecutionContext`.

**По ADR §3.0 — это предусловие №1 tenancy-аддона.** Сперва вынести auth из
хардкод-токена в **инъектируемый шов** (протокол / Integrant-ключ): core держит
дефолтную реализацию (single-token), аддон её *переопределяет* своей
(session/JWT → org/user). Без этого шва аддон не сможет вклиниться чисто. То
есть «таблица user + сессии» едет в аддон, а core получает лишь точку замены.

### 4.2. Права: минимальные примитивы, НЕ большая система (ответ на твой вопрос)

Этос graphden (#2, #6) требует минимума сущностей. Достаточно **одного
примитива**:

```
grant(subject, capability, scope)
  subject    = user | group
  capability = :read | :write | :execute | :bind-args | :append-list
             | :publish | :install | :admin
  scope      = поддерево неймспейса (или конкретная fn)
```

- **Группы пользователей** = множества user'ов (одна junction-таблица).
- **Группы функций** = уже существующие **неймспейсы** (бесплатно, дерево).
- Сложные кейсы покрываются **комбинацией** грантов, а не новыми сущностями.

### 4.3. Ограниченное редактирование (кейс «спам-фильтр на пользователя»)

«Пользователь меняет только некоторые аргументы / добавляет-удаляет элементы
списка там же, где добавил, не через наследование» раскладывается так:

- `:bind-args` (scope=ns) — можно менять `binding.value`, нельзя
  `ref-fn-id`/`type-override`/полную замену.
- `:append-list` (scope=ns) — можно добавлять/удалять элементы своего
  `binding-list-item`, не трогая родительские.
- **`:terminal`-флаг** (запечатать слот от переопределения потомками) —
  ограничивает, что трогать **нельзя**.
- «Не видит чужие спам-фильтры» = `:read`-скоуп + **личный неймспейс на
  пользователя** (его фильтры там; гранты на чтение — пер-неймспейсные).

**Критично (R2):** `:terminal` и `:list-append` **задокументированы, но НЕ
реализованы** (нет ни поля в схеме, ни энфорсмента). Весь кейс ограниченного
редактирования зависит от их реальной постройки. Это предусловие фазы 3.

### 4.4. Workspaces = объединение видимых неймспейсов

Workspace пользователя/контекста = множество неймспейсов, на которые есть
`:read`-грант. «Установка пакета» (2.8) = добавление read-гранта на его
неймспейс. Так пакеты + workspaces + права — один механизм.

## 5. Гейтинг эффектов (сквозной, предусловие облака) — самый важный пункт

Сегодня (проверено): base-fn вызывают `(record-effect! :env)` и т.п. — но это
**чисто информационно** (type-checker + чипы в UI). Рантайм-гейта/песочницы
**нет**: `ctx` доступен в каждом base-fn, но его никто не спрашивает «можно ли».

Дизайн (два слоя, belt-and-suspenders):

- **Рантайм-гейт:** в `ExecutionContext` добавить `:allowed-effects`.
  `record-effect!` проверяет `(contains? allowed eff)` и кидает
  `:execution/forbidden-effect`. Для облачных org-контекстов из allowed
  исключены `:env`, `:io`, `:network` (или `:network` сужен до egress-allowlist).
  Для self-hosted/mixed allowed = все.
- **Видимость в реестре (edit/sync-time):** билд-тайм фильтрация base-fn реестра
  — запрещённые примитивы вообще не зарегистрированы/не видны в облачном
  контексте (fn-picker не покажет `:env`, sync упадёт на «unknown fn»).

Только это делает «облачный юзер не читает env/файлы, не ходит во внутреннюю
сеть» **реальным**, а не декларативным. «Поднять свою БД в нашем облаке/приватной
сети» — решается **политиками кубера/сети**, а не сервисом (ты прав); на уровне
app достаточно гейта эффектов + egress-allowlist.

### Статус реализации (обновлено)

**Сделано (Phase 1.5):**

- **Рантайм-гейт — РЕАЛИЗОВАН.** `ExecutionContext :allowed-effects` (set;
  nil = unrestricted) → `compile-runtime/execute` биндит `*allowed-effects*` →
  `record-effect!` кидает `:execution/forbidden-effect`. Perf: unrestricted =
  ноль overhead. Тест + smoke зелёные.
- **Coverage-аудит — ПРОЙДЕН.** Все 275 base-fn проверены: каждый
  security-sensitive (`:env`/`:io`/`:network`/`:process`) зовёт `record-effect!`
  → **0 дыр в sandbox**. `:process` = thread/server/cancel (контроль), shell/RCE
  примитива нет. Один `:db`-gap (layout cache) починен.
- **Артефакты:** `compile-runtime/cloud-forbidden-effects` `#{:env :io :network
  :process}` + `default-cloud-allowed-effects` `#{:db :time :state :random}`
  (вычисляется как `known-effects − forbidden`).

**Wiring — ОТЛОЖЕН В PHASE 2 (осознанное архитектурное решение).** Глобальный
флаг на default-ctx НЕ работает: дефолтный ctx исполняет САМУ платформу
(web-server `:network`/`:process`, vault `:network`, config `:env`, asset-reads
`:io`) — рестрикт дефолтного ctx ломает платформу. Граница «platform vs user
execution» — это и есть граница тенантности. Гейт **ctx-based по дизайну**,
поэтому правильная точка установки — **per-org ExecutionContext** (фаза 2,
§3.1): user-граф исполняется в org-ctx с `:allowed-effects
default-cloud-allowed-effects`, platform-ctx остаётся unrestricted. Когда org-ctx
появится, wiring — одна строка через существующий механизм. Частичный wiring
(гейт только `/api/execute` через биндинг в `run-future`) был отвергнут как
параллельный механизм, не композирующийся с ctx-дизайном (стал бы долгом).

## 6. Монетизация (через систему пакетов — да, реализуемо)

Система пакетов + организации — естественный субстрат для тарифов:

| Тариф            | Что открывает                                                        |
| ---------------- | ------------------------------------------------------------------- |
| Free             | публичные fns-пакеты, наши base-fn, одна организация, лимит compute/storage |
| Paid             | приватные пакеты, право publish, кастомные домены, больше storage (строк графа), больше service-слотов/compute, egress-allowlist, сторонние impl-пакеты (mixed), SSO для организаций |
| Self-hosted/Mixed| оплата за объём хранения графа у нас + storage API + egress         |

Реестр пакетов — естественная точка paywall (gate на publish/install приватных
и премиум-пакетов). Смешанный режим (bring-your-own-executor) — сам по себе
платная фича. Это **не убивает проект**, а наоборот — даёт несколько ортогональных
рычагов монетизации, не ломая бесплатный self-hosted путь.

| **R1** | **Гейтинга эффектов нет.** «Пакеты без impl» ≠ безопасность. Облачный юзер композит существующих эффектных base-fn. Надо строить рантайм-гейт. Без него вся облачная модель безопасности — фикция. |
| **R2** | `:terminal` и `:list-append` **задокументированы как реальные, но не реализованы** (ни поля, ни энфорсмента). Кейс ограниченного редактирования зависит от них. |
| **R3** | **Нет round-trip экспортёра** граф→EDN. И publish, и export его требуют. |
| **R4** | `impl-hash` — заглушка `nil`. Детекция breaking-change между версиями пакета слепа. |
| **R5** | `org-id` на каждой таблице — **в напряжении с принципом #2** (минимум полей). Нужен ADR. |
| **R6** | **Чтение сегодня полностью анонимно** — каждый read-эндпоинт открыт. Мультитенант → КАЖДЫЙ read-путь должен стать org-scoped. Поверхность огромна и хрупка → RLS обязателен как нижний предохранитель. |
| **R7** | Смешанный режим: наш storage API при баге не должен отдать чужие данные → API тоже под RLS, не только app-проверки. Их executor исполняет их эффекты — это их зона; наша зона — только скоуп storage API. |
| **R8** | LRU-кэш per-branch хендлеров (`max 16`) **протечёт между организациями**, если не сделать его per-org. Конкретный баг. |
| **R9** | Vault/секреты **глобальны** — все аутентифицированные видят все. Нужен org/user-скоуп путей секретов; сегодня его нет. |
| **R10**| Проверка владения доменом — сетевой **эффект**, запрещённый облачным юзерам. Значит fn-проверки — привилегированная платформенная, не пользовательская. Ломает наивное «через граф». |
| **R11**| Два разных роутинга смешиваются: поддомен организации → тенант (editor/API) и hostname развёрнутого веб-сервера → `:service`. Это разные отображения. |
| **R12**| **Уникальность имён** сегодня `UNIQUE(namespace-id, name)` + глобально-в-батче (валидатор). Мультитенант → sync-валидатор должен скоупиться per-org, иначе две организации не смогут иметь fn с одинаковым именем даже в своих неймспейсах. |
| **R-NS**| **M2M для неймспейсов не реализован** (вопреки памяти — `fn.namespace-id` единственный FK, `:ns` — дерево). Это упрощает упаковку, но твой interface-gathering кейс потребует НОВОЙ сущности (нарушает #2) и сейчас не существует. |
| **R13**| Замена `AUTH_TOKEN` (общий пароль) на per-user — крупная переделка auth (таблица user + сессии/JWT + проброс контекста). Нельзя недооценивать объём. |

## 8. Последовательность реализации

Обновлено с учётом ADR §3.0: фазы 2–3 (организации + пользователи/права)
переосмыслены как **постройка опционального tenancy-аддона**, а не «фичи в
ядре».

- **Фаза 0 (подготовка):** ADR по `org-id` vs #2 (R5) — **зафиксирован §3.0**;
  модель неймспейсов (R-NS) — подтверждена single-membership; гейт эффектов
  (R1) — самостоятелен, сделан параллельно.
- **Фаза 1 (пакеты) — ✅ СДЕЛАНО:** round-trip экспортёр (R3) → scoped
  `export-namespace` + извлечение зависимостей → реестр `:package-version` +
  **publish/list/fetch/install** (граф-композировано) → 6 layering-фиксов
  (core/web публикуются независимо). **Осталось:** реальный `impl-hash` (R4),
  версионные констрейнты, расщепление каналов impl/fns, `executor-packages.edn`
  манифест (он же — механизм инъекции аддонов, см. §3.0 нюанс 3), вынос
  доменных пакетов (§2.9), hot-recompile при install.
- **Фаза 1.5 (гейт эффектов, R1) — ✅ МЕХАНИЗМ СДЕЛАН:** `:allowed-effects` в
  ctx + проверка в `record-effect!` + coverage-аудит (0 дыр) +
  `cloud-forbidden-effects`/`default-cloud-allowed-effects`. **Проводка
  отложена в аддон** (§3.0, §5): глобальный флаг на default-ctx ломает
  платформу. Билд-тайм фильтрация реестра — второй слой, follow-up.
- **Фаза 2–3 (tenancy-аддон, по §3.0):** строго в порядке предусловий —
  1. **auth-шов** (R13) — ✅ **СДЕЛАНО** (ветка `feature/auth-seam`):
     `graphden.auth.provider/AuthProvider` протокол + дефолтный
     `SingleTokenAuthProvider`; Integrant-ключ `:auth/provider`; ctx-опт
     `:auth-provider`; graph-шов `:authenticate-request` →
     `:request-authenticated?`. Аддон переопределяет `:auth/provider`.
  2. **манифест аддонов** — ✅ **СДЕЛАНО**: `config/read-config` deep-мержит
     Aero-фрагменты аддонов из `GRAPHDEN_ADDON_CONFIGS` (env, comma-sep
     classpath-ресурсы) поверх core-конфига; фрагмент аддона переопределяет
     indirection-ключи (напр. `:auth/provider`) + добавляет свои; директива
     `:graphden/require` грузит init-key-неймспейсы аддона. Без аддонов —
     no-op (single-tenant). (Заменяет набросок `executor-packages.edn`.)
  3. **`OrgScopedStorage` + RLS** (R6, оба слоя) — ✅ **ПОСТРОЕНО И
     ПРОТЕСТИРОВАНО** (B1–B5, ветка `feature/auth-seam`):
     - *storage-seam* `:app/storage` (Integrant identity-passthrough) ПОД
       versioning, чтобы `vs/unwrap` сохранял tenant-фильтр (нюанс 1);
     - **B1** `OrgScopedStorage`-декоратор (own+public read, own write,
       штамп org, делегирует 8 протоколов);
     - **B2** `org-id`-колонка на всех 5 graph-сущностях (identity-level,
       NULL≡public, не versioned);
     - **B3** `:org/scoped-storage` init-key + addon-фрагмент → `Versioned(
       OrgScoped(Postgres))` через манифест (real-Postgres интеграция);
     - **B4** `:request-scope` шов → `dispatch` биндит `*current-org*` из
       auth-principal per-request;
     - **B5** Postgres RLS — own+public/own policy + `set_config`-сеттер,
       enforcement доказан raw-query тестом через `SET ROLE` (non-superuser);
     - **provider** `tenancy.auth/TokenAuthProvider` резолвит bearer →
       `{:user :org}` (hashed-token lookup); цепочка `token → org →
       *current-org* → OrgScoped + RLS` доказана end-to-end.
     - **ops: datasource-wrap ✅** `rls/org-aware-datasource` оборачивает
       пул `:db/postgres` (seam `:datasource-wrap`), ставит
       `graphden.current_org` из `*current-org*` на каждом borrow (tenant →
       org, public/admin/unbound → '' = видит всё); доказано тестом.
     - **ops: enable-rls! автозапуск ✅** `:tenancy/rls-enabler` Integrant-
       компонент (зависит от `:db/postgres` → таблицы уже созданы) ставит
       политики на boot; доказано (policy на всех 5 scoped-таблицах).
     *Остаётся чистый деплой/инфра:* приложение под non-superuser ролью
     (superuser обходит RLS); реальный token-source (storage/secret вместо
     static-map). Дальше по плану: per-org LRU (R8) → org-скоуп секретов
     (R9) → поддомены (R10, R11);
  4. **проводка effect-gate** — ✅ **СДЕЛАНО**: request-scope wrap для
     реального тенанта (org ≠ public) биндит `cr/*allowed-effects*
     default-cloud-allowed-effects` вокруг хендлера → cloud-граф не может
     env/io/network/process. `execute` re-биндит `*allowed-effects*` только
     из ctx (у branch-ctx его нет), поэтому ambient-биндинг проходит до
     `record-effect!`. Platform (public/admin) — без ограничений.
     Доказано: тенант env/network → throw, db/time → ok; public —
     unrestricted; binding восстанавливается (no leak). *(Реализация через
     dynamic var per-request, а не «:allowed-effects на ctx» — ctx общий
     per-branch, org — per-request.)*
  5. **`grant`-примитив** (§4.2) — ✅ **ПРИМИТИВ ГОТОВ**:
     `tenancy.grant` — `(subject, capability, namespace)`, `can?`
     (default-deny; `:admin` ⇒ остальные capabilities; ns-grant покрывает
     потомков по dot-path; root = blank ns), `GrantStore` протокол +
     static-map impl + `:tenancy/grant-store` init-key + `authorized?`
     мост от auth-principal (`:user`). Доказано (5 тестов / 17 ассертов).
     - **enforcement ✅ (opt-in)** request-scope wrap при наличии
       `:grant-store` гейтит write/execute тенанта: `request->capability`
       (POST/PUT/PATCH/DELETE→write, `/execute`→execute, else read) +
       `request-permitted?` → 403 если нет права на org; reads открыты
       (OrgScoped рулит видимостью); platform не гейтится. Доказано.
     - **UI-сигнал ✅** request-scope вешает `X-Graphden-Capabilities`
       (comma-list: `write,execute` / подмножество / пусто) на каждый
       non-403 ответ — контракт, который редактор читает, чтобы прятать
       affordances. Доказано (tenant с `:write` → "write", без грантов →
       "", platform → "write,execute").
     - **editor-JS gating ✅** fetch-wrap читает `X-Graphden-Capabilities`
       с каждого /api-ответа → `graphdenCapabilities` + body-классы
       `gd-no-write`/`gd-no-execute`; CSS прячет `.more-actions-trigger`
       (вход в ✎/+/✕/▶) при `gd-no-write`. Без аддона header отсутствует →
       классы не ставятся → редактор без изменений. **Проверено Playwright
       на localhost:9002:** редактор грузится чисто (fetch-wrap безопасен),
       `graphdenCanWrite()` = true без header, CSS-гейт прячет affordance.
     - **per-target-namespace ✅** request-scope теперь coarse-гейт
       (`has-capability?` — «писатель/исполнитель вообще?»), а ТОЧНУЮ
       проверку делает storage-слой (`tenancy.authz/authorize-writer`):
       резолвит ns-path из дерева `:ns` (name+parent-id), проверяет грант
       против реального target-namespace, бросает `:authz/forbidden` →
       request-scope ловит → 403. `*current-principal*` биндится в
       request-scope. Доказано: unit (ns-path/writable?/guard) + **real-
       Postgres** (alice с грантом на acme.team пишет туда, но не в acme;
       admin/public не гейтится). Скоуп: `:fn`-записи с `:namespace-id`;
       прочие сущности/update без ns-id — coarse-гейт + RLS (follow-up).
     - **storage-backed store ✅** новый seam `:db/schema {:extensions […]}`
       (addon добавляет сущности без правки ядра) → `:grant`-entity
       (`graphden.tenancy.grant-schema`) + `StorageBackedGrantStore` читает
       `:grant`-строки (capability text→keyword), `:tenancy/grant-store`
       полиморфен (`:storage` → storage-backed, `:grants` → static).
       Доказано: unit (extend-builder, seam, store) + **real-Postgres**
       (`:grant`-таблица, roundtrip, `can?`); boot backward-compat. Гранты
       теперь обычные entity → CRUD через `/api/entities/grant`.
     - **per-action gating ✅** CSS по `data-action` в popover: `gd-no-write`
       прячет write-экшены (rename/extend/delete/mi-parent/ns-move/use-site/
       service-settings), `gd-no-execute` — `run-fn`; read-экшены
       (i/↗/⌛) всегда видны; full read-only (нет write И execute) прячет
       сам `⋯`-вход. **Проверено Playwright:** execute-only прячет write +
       показывает run; write-only прячет run; read-only прячет вход.
     - **per-namespace execute ✅** инъектируемый `:execute-guard` на ctx;
       `cr/execute` консультирует его ОДИН раз на top-level (recursion-flag
       `*execute-authorized*` держит его вне hot sub-fn пути), throw
       `:authz/forbidden` → 403-bridge. `authz/authorize-executor` резолвит
       namespace fn'а (read :fn → namespace-id → ns-path) + проверяет
       `:execute`; skip для public/admin + system (нет principal). Доказано:
       unit (guard по namespace, fires-once, denial/skip) + execute_http
       (реальный /api/execute через dispatch) + boot backward-compat.
     - **личные неймспейсы ✅** `grant/with-personal-namespaces` —
       GrantStore-декоратор: каждый юзер неявно держит `:admin` на
       `<prefix>.<user>` (напр. `users.alice`), без grant-строки;
       композируется со static/storage-backed store; `:personal-ns-prefix`
       в `:tenancy/grant-store`. Доказано: юзер владеет своим ns +
       потомками (все capabilities), не владеет чужим, base-гранты
       сохраняются. *(Provisioning самой `:ns`-сущности — follow-up.)*
     - **workspaces ✅ (backend)** `grant/workspace` — union именованных
       namespace'ов из грантов юзера (+ personal через декоратор; root/blank
       и public исключены); сортированный set. Surface через
       `X-Graphden-Workspace` header в request-scope (tenant → его
       namespace'ы, platform → пусто). Доказано: pure + header через
       dispatch. **editor-frontend ✅** fetch-wrap читает header →
       `graphdenWorkspace` + `window.graphdenInWorkspace(path)`; sidebar
       вешает `.ns-in-workspace` на ns-header в workspace → CSS left-accent.
       Без аддона — no-op. **Проверено Playwright:** helper есть, no-op без
       workspace, CSS-акцент 2px, matching (exact+descendant да, parent/
       sibling нет).
     *Остаётся:* `:terminal`/`:list-append` (R2);
  6. **продуктовый fns-пакет** «org-admin» (UI организаций/юзеров/грантов),
     зависит от сущностей аддона.
     - **fns-channel seam ✅** `:app/packages {:extra-package-names […]}` —
       аддон добавляет свои fns-пакеты через манифест, не переписывая
       core-список; грузятся ТОЛЬКО при активном аддоне (§2.1). Доказано:
       extra грузится вместе с core, no-extra без изменений, boot ок.
       *Это разблокирует org-admin UI как `tenancy-admin` fns-пакет.*
     *Остаётся (org-admin UI):* граф-композированная grants-admin панель
     (query `:grant` → таблица + create/delete, route, editor-JS mount —
     по образцу secrets-panel ~200 fn-defs); тестируется только при
     активном аддоне (full sync + `:grant`). Крупная продуктовая фича.
- **Фаза 4 (распил/смешанный режим):** протоколы + deps.edn git-deps;
  смешанный режим = композиция «org-scoped storage API» + «их executor».
  Polylith — опционально, не блокер.

> **Фаза 1 + 1.5 — закрыты этой сессией** (16 коммитов пакетов + гейт). Фазы
> 2–3 — это **один tenancy-аддон** по плану §3.0; начинать строго с auth-шва
