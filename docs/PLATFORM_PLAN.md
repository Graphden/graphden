# PLATFORM_PLAN.md — Пользователи, организации, пакеты, права

> Статус: **DESIGN / ROADMAP**. Это план, а не описание существующего кода.
> Ветка реализации: `feature/platform-packages-tenancy`.
> Цель документа — зафиксировать целостную картину для четырёх переплетённых
> фич (пакеты, организации, пользователи, права), последовательность их
> внедрения и список архитектурных рисков, прежде чем писать код.

## 0. Резюме для занятых

Четыре фичи связаны, но **разделяемы**. Рекомендуемый порядок:

1. **Пакеты** (самая автономная, начинаем с неё) — реестр + publish/install +
   round-trip экспорт + версии пакетов поверх существующих веток графа +
   расщепление канала распространения impl/не-impl.
2. **Тенантность / организации** — `org-id` по образцу `branch-id`, два слоя
   изоляции (app-decorator + Postgres RLS), поддомены и кастомные домены.
3. **Пользователи и права** — модель пользователя вместо общего пароля +
   минимальный примитив `grant(subject, capability, ns-scope)`.
4. **Распил монолита** (будущее) — через протоколы + deps.edn git-deps, НЕ через
   Polylith как обязательное условие.

**Главный вывод, меняющий рамку всей задачи:** граница безопасности облака —
это **НЕ «пакеты без impl»**, а **гейтинг эффектов в рантайме executor'а**,
которого сегодня нет (см. §1 и риск R1). «Пакеты без impl» — условие
необходимое, но недостаточное.

**Второй вывод, упрощающий модель:** оси не три («облако / self-hosted /
смешанный»), а **две независимые**: где живёт граф и где крутится executor.
Смешанный режим тогда раскладывается в уже понятные части (см. §1).

## 1. Три типа пользователей → две оси

Вместо трёх «типов» удобнее думать о матрице 2×2:

|                          | Executor: наш                     | Executor: пользователя             |
| ------------------------ | --------------------------------- | ---------------------------------- |
| **Граф (fn-строки): наш**| **Облачный** (тип 1)              | **Смешанный** (тип 3)              |
| **Граф: пользователя**   | (нет смысла — пропускаем)         | **Self-hosted** (тип 2)            |

Что это даёт:

- **Облако:** весь impl — *наш* код. Пользователь никогда не присылает Clojure.
  Но он **компонует существующие base-fn**, часть которых выполняет эффекты
  (`:env`, `:read-resource`, сетевые, `:pg-query`). Значит безопасность ≠
  «нет impl», а «executor не даёт выполнить запрещённый эффект» → **гейтинг
  эффектов** (R1).
- **Self-hosted:** executor — *их*. Любой impl — их ответственность. Наша
  поверхность — ноль.
- **Смешанный** = *наш storage API (со скоупом по ключу организации)* +
  *их executor (self-hosted-стиль)*. То есть смешанный режим **не новая
  сущность**, а композиция: «org-scoped storage API» (фаза 2) + «их executor»
  (фаза 4). Гейтинг эффектов в смешанном — их забота, не наша; наша забота —
  чтобы storage API **никогда** не отдал чужие данные даже при баге (→ RLS).

Вывод: смешанный режим **реализуем** и почти бесплатен, если фазы 2 и 4 сделаны
правильно. Отдельного кода под него почти не нужно.

## 2. ФАЗА 1 — Пакеты

### 2.1. Два канала распространения (ключевое разделение)

| Канал                       | Что распространяет                                  | Механизм                              | Кто может ставить в облаке |
| --------------------------- | --------------------------------------------------- | ------------------------------------- | -------------------------- |
| **Impl-канал**              | пакеты с `impls.clj` (Clojure-код, новые примитивы) | git-репозиторий / Maven (deps.edn)    | **никто** (это код на нашем executor) |
| **Fns-канал**               | пакеты только с `fns.edn` (композиции над impl)     | наш реестр, EDN по HTTP → строки графа| **да** (это данные, не код), при условии гейтинга эффектов |

Почему так:

- impl-пакет = новый Clojure-код → может выполнить что угодно на executor'е,
  где он скомпилирован. В облаке его собираем **только мы**, и делаем доступным
  всем. Self-hosted/смешанный пользователь добавляет его в **свой** executor.
- fns-пакет = только описание композиций (строки `fn/slot/binding`). Установка =
  sync EDN в граф. Никакого выполнения кода. Поэтому облачный пользователь может
  ставить fns-пакеты сам — но что он может ими *делать*, ограничивает гейтинг
  эффектов (R1), а не факт наличия impl.

Любой fns-пакет транзитивно зависит хотя бы от одного impl-пакета (у любой fn
самый древний предок — base-fn с impl). Это становится **объявленной
зависимостью пакета** (см. 2.3).

### 2.2. Распространение impl-пакетов: deps.edn git-deps, НЕ Polylith, НЕ submodules

Рекомендация (ответ на вопрос про Polylith):

- **Распространение impl-пакетов** — нативный механизм Clojure: каждый impl-пакет
  это свой git-репозиторий с `package.edn` + `impls.clj` + `deps.edn`.
  Self-hosted пользователь добавляет git/Maven-координату. Это и есть «обычные
  git-репозитории и clojure-библиотеки», как ты и предполагал.
- **Автоматизация «добавил в одном месте — сборка подхватила»**: вводим
  манифест `executor-packages.edn` (список координат пакетов). Шаг сборки
  (`build.clj`) сплайсит его в `deps.edn` `:deps`/`:extra-deps` и в список
  загружаемых пакетов loader'а. Пользователь правит **один файл данных**, не
  трогая код executor'а → меньше шанс случайно сломать executor. Ровно та
  автоматизация, которую ты хотел.
- **Polylith** — это инструмент организации монорепы (components/bases/projects).
  Он *помог бы* структурировать наши компоненты, но **не требуется** для
  swappability: кодовая база уже протокол-ориентирована (`StorageCRUD`,
  `ExecutionGraph`, `data-schema-protocol`, integrant). Swappability даёт
  протокол + integrant, а не Polylith. Вердикт: **Polylith — приятно потом,
  не блокер сейчас.** Не закладываемся.
- **Git submodules** — не использовать. deps.edn git-deps — clojure-нативный
  эквивалент, без боли submodule'ов.

### 2.3. Версии и зависимости пакетов

Сегодня (проверено): `package.edn` имеет `:dependencies ["core" ...]` — голые
имена без версий; топосортировка зависимостей уже есть; `:version` — чистая
метадата, в рантайме не используется; `impl-hash` — заглушка `nil`.

Что добавляем:

- **Версионные констрейнты** в `:dependencies`: `{"core" ">=1.5.0"}`.
  `resolve-dependencies` (loader.clj) проверяет и тянет из реестра.
- **Реальный `impl-hash`** (SHA-256 канонической формы impl) — нужен для
  детекции breaking-change при смене версии impl-пакета (R4). Сейчас всегда nil.
- **Проверка при установке**: нельзя поставить fns-пакет, чьи узлы ссылаются на
  отсутствующих предков. resolver проверяет наличие пакетов-зависимостей в
  целевой системе и при необходимости тянет и ставит их (рекурсивно).

### 2.4. Три системы версий и как они соотносятся

| Система                         | Что версионирует            | Существует? |
| ------------------------------- | --------------------------- | ----------- |
| **Ветки графа** (git-подобные)  | per-entity версии fn-строк  | да          |
| **Версии пакетов** (semver)     | снимок EDN-бандла           | метадата    |
| **Версии git-репо** (impl)      | git-тег / Maven-версия      | стандарт    |

**Главная синергия (важно):** «проверить новую версию пакета на тестовой ветке
перед продом» = **поставить новую версию пакета на ветку графа**, прогнать тесты,
затем смержить в `main`. Откат = revert merge или переустановка старой версии.
То есть существующая система веток графа **уже является** стейджингом для
апгрейда пакетов. Ничего нового изобретать не надо — переиспользуем ветки.

- Импорт версии «из dev/другой ветки» = установка на соответствующую ветку графа.
- Уведомления о новых версиях = реестр хранит latest; периодическая сверка
  installed-version vs registry-latest по организации.
- «У пакета может измениться только impl» → это про impl-канал: новая версия
  Maven/git-координаты, ловится по `impl-hash`-дрифту.

### 2.5. Реестр (PyPI-подобный) и публикация

- **Реестр fns-пакетов** — сервис: пакет = именованный версионированный бандл
  `fns.edn` (+ вложенные неймспейсы как структура папок). Публичный или
  доступный по ключу организации. Просмотр описаний/версий — как pypi.org.
- **Публикация облачным пользователем БЕЗ создания файла руками**: API
  `POST /api/packages/publish` принимает корневой неймспейс → сервер
  **сериализует поддерево графа в EDN** (см. 2.6) → сохраняет как версию пакета.
  Пользователь не возится с git/файлами.
- **Публикация self-hosted пользователем независимо от нашего реестра**: тот же
  экспортёр выдаёт `fns.edn` (или набор с папками для вложенных ns) → пользователь
  кладёт в свой git. Реестр — опционален.

### 2.6. Round-trip экспортёр `граф → fns.edn` (отсутствует, нужен)

Сегодня (проверено): сериализации графа обратно в EDN **нет вообще** — система
односторонняя (EDN → строки). И publish, и export требуют этого. Это
**фундаментальная подзадача фазы 1**: обратный проход к парсеру `records`
(`fn/slot/fn-slot/binding/binding-list-item` → `fns.edn`-формы). Хорошо
ограничена по объёму.

### 2.7. Пакеты ↔ неймспейсы (с учётом реальной схемы)

**Поправка к твоему вопросу:** в текущей схеме связь fn↔namespace —
**один-к-одному** (`fn.namespace-id` — единственный FK), а `:ns` — дерево
(`parent-id`). M2M, который ты помнишь («одна fn в разных неймспейсах»), в
схеме **не реализован** (см. R-NS). Поэтому неоднозначности «к какому неймспейсу
относить при упаковке» сегодня нет.

Модель:

- **Пакет = именованный версионированный экспорт поддерева неймспейса** (один
  корневой ns + его дочерние). Замыкание fn под корнем + их зависимости из
  других неймспейсов → становятся **объявленными зависимостями пакета**.
- Если/когда m2m для неймспейсов появится (для твоего interface-gathering
  кейса — «собрать все места, где нужны секреты»), то такой **сборочный
  неймспейс-вид — НЕ пакет**, а представление (view). Паковать его смысла нет
  (ты сам это и заметил). Для упаковки нужно понятие «домашний неймспейс»
  (primary membership); вторичные membership в пакет не входят.

### 2.8. «Установка» для облака = грант видимости, а не дублирование строк

Облачный пользователь **не должен** дублировать у себя файлы/строки публичного
пакета. Поэтому:

- Публичные fns-пакеты живут один раз в **public-организации** (общий тенант).
- «Установка пакета» облачным пользователем = **грант на чтение** неймспейса
  этого пакета в его **workspace** (см. фазу 3, §4.4). Строки не копируются.
- Это прямо отвечает на твою догадку: «установка пакета связана с настройкой
  видимости неймспейсов». Пакеты, workspaces и права **унифицируются через
  ns-scoped гранты**.
- Форк/модификация публичного пакета = copy-on-write в свой неймспейс (тогда
  строки копируются, но только при намеренном форке).

### 2.9. Что вынести из текущего репозитория

После появления системы пакетов в ядре оставляем **минимально необходимое**:
executor, storage, versioning, packages-loader, web-примитивы, server-скелет,
ядро base-fn. Кандидаты на вынос в отдельные репозитории/пакеты:
доменные/примерные пакеты, нестандартные impl-пакеты, возможно сам editor
(это продукт, но технически — app-пакет). Цель — уменьшить объём и шум ядра.

## 3. ФАЗА 2 — Организации и тенантность

### 3.1. Изоляция данных: `org-id` по образцу `branch-id`, два слоя

Существующий `branch-id` — точный аналог тенант-скоупа (проверено:
`VersionedStorage` оборачивает storage и автофильтрует по `branch-id`).
Зеркалим его:

- **Слой A (app): `OrgScopedStorage`-декоратор** (как `VersionedStorage`) —
  инжектит фильтр `org-id` в каждый запрос. Эргономика и перф.
- **Слой B (БД): Postgres RLS** — `SET LOCAL app.current_org = ?` в начале
  каждой транзакции (HikariCP пулит коннекты, поэтому именно `SET LOCAL`
  внутри транзакции / `set_config(...,true)`, а не session-level onConnect).
  Это **жёсткая гарантия «даже если в нашем коде баг»**, которую ты и хочешь.

**Делаем оба.** RLS — нижний предохранитель (см. R6: сегодня чтение полностью
анонимно, поверхность огромна, app-слой что-то да пропустит). Org-id ставим
колонкой на `fn` и версионные таблицы; для публичных пакетов — спец-организация
`public`. Это **в напряжении с принципом #2** (минимум полей) — нужен явный ADR
(R5): тенант — легитимное сквозное поле, не семантика графа.

### 3.2. Поддомены организаций и кастомные домены (Heroku-стиль)

Сегодня (проверено): `Host`-заголовок не инспектируется; роутинг по веткам идёт
через `X-Graphden-Branch` / `?branch=`. Шов — `branch_router/dispatch` +
`extract-branch-ref`.

- **Авто-поддомен при регистрации организации**: `<org>.graphden.app` → тенант
  организации. Расширяем извлечение контекста: парсим поддомен из `Host` →
  резолвим в `org-id` (таблица `subdomain → org`). Маршрут создаётся
  автоматически при создании организации.
- **Кастомные домены**: таблица `hostname → org`. Пользователь добавляет домен;
  **подтверждение владения** — DNS TXT-запись, которую мы один раз проверяем.
- **Важно (R10):** проверка DNS — это сетевой **эффект**, который облачным
  пользователям запрещён. Значит fn проверки домена — **привилегированная
  платформенная fn**, а не пользовательская композиция. «Через граф, но не
  пользователем» — тонкость, ломающая наивное «желательно через граф».
- **Важно (R11):** различаем два роутинга — (а) поддомен организации → тенант
  (editor/API) и (б) hostname развёрнутого пользователем веб-сервера → его
  `:service`. Это **разные** отображения, нельзя схлопывать в одно.

### 3.3. Пользовательские веб-серверы на поддомене (уже почти готово)

Сервисная модель уже умеет per-branch (проверено: `:service.branch-id` +
per-branch `ExecutionContext`, reconciler). Пользователь делает fn-def
`:parent :http-server` со своим `:handler`, заводит `:service` со своим
скоупом; reconciler поднимает его в нужном контексте; роутер направляет
запросы с подходящим hostname в этот сервис. Per-tenant runtime-config
(порт/путь) изолируется через уже существующий `:branch-local?`.

**Конкретный баг-риск (R8):** LRU-кэш per-branch хендлеров (`max 16`) должен
стать **per-org**, иначе ветки/хендлеры протекают между организациями.

## 4. ФАЗА 3 — Пользователи и права

### 4.1. Аутентификация: заменить общий пароль

Сегодня (проверено): единственный `AUTH_TOKEN` (env) как bearer в localStorage,
никакой модели пользователя; **чтение вообще анонимно**; секреты — все видят все.
Это полная переделка auth: таблица `user`, сессии/JWT, извлечение
user-контекста в middleware (`ring-adapter`), проброс в `ExecutionContext`.

### 4.2. Права: минимальные примитивы, НЕ большая система (ответ на твой вопрос)

Этос graphden (#2, #6) требует минимума сущностей. Достаточно **одного
примитива**:

```
grant(subject, capability, scope)
  subject    = user | group
  capability = :read | :write | :execute | :bind-args | :append-list
             | :publish | :install | :admin
  scope      = поддерево неймспейса (или конкретная fn)
```

- **Группы пользователей** = множества user'ов (одна junction-таблица).
- **Группы функций** = уже существующие **неймспейсы** (бесплатно, дерево).
- Сложные кейсы покрываются **комбинацией** грантов, а не новыми сущностями.

### 4.3. Ограниченное редактирование (кейс «спам-фильтр на пользователя»)

«Пользователь меняет только некоторые аргументы / добавляет-удаляет элементы
списка там же, где добавил, не через наследование» раскладывается так:

- `:bind-args` (scope=ns) — можно менять `binding.value`, нельзя
  `ref-fn-id`/`type-override`/полную замену.
- `:append-list` (scope=ns) — можно добавлять/удалять элементы своего
  `binding-list-item`, не трогая родительские.
- **`:terminal`-флаг** (запечатать слот от переопределения потомками) —
  ограничивает, что трогать **нельзя**.
- «Не видит чужие спам-фильтры» = `:read`-скоуп + **личный неймспейс на
  пользователя** (его фильтры там; гранты на чтение — пер-неймспейсные).

**Критично (R2):** `:terminal` и `:list-append` **задокументированы, но НЕ
реализованы** (нет ни поля в схеме, ни энфорсмента). Весь кейс ограниченного
редактирования зависит от их реальной постройки. Это предусловие фазы 3.

### 4.4. Workspaces = объединение видимых неймспейсов

Workspace пользователя/контекста = множество неймспейсов, на которые есть
`:read`-грант. «Установка пакета» (2.8) = добавление read-гранта на его
неймспейс. Так пакеты + workspaces + права — один механизм.

## 5. Гейтинг эффектов (сквозной, предусловие облака) — самый важный пункт

Сегодня (проверено): base-fn вызывают `(record-effect! :env)` и т.п. — но это
**чисто информационно** (type-checker + чипы в UI). Рантайм-гейта/песочницы
**нет**: `ctx` доступен в каждом base-fn, но его никто не спрашивает «можно ли».

Дизайн (два слоя, belt-and-suspenders):

- **Рантайм-гейт:** в `ExecutionContext` добавить `:allowed-effects`.
  `record-effect!` проверяет `(contains? allowed eff)` и кидает
  `:execution/forbidden-effect`. Для облачных org-контекстов из allowed
  исключены `:env`, `:io`, `:network` (или `:network` сужен до egress-allowlist).
  Для self-hosted/mixed allowed = все.
- **Видимость в реестре (edit/sync-time):** билд-тайм фильтрация base-fn реестра
  — запрещённые примитивы вообще не зарегистрированы/не видны в облачном
  контексте (fn-picker не покажет `:env`, sync упадёт на «unknown fn»).

Только это делает «облачный юзер не читает env/файлы, не ходит во внутреннюю
сеть» **реальным**, а не декларативным. «Поднять свою БД в нашем облаке/приватной
сети» — решается **политиками кубера/сети**, а не сервисом (ты прав); на уровне
app достаточно гейта эффектов + egress-allowlist.

## 6. Монетизация (через систему пакетов — да, реализуемо)

Система пакетов + организации — естественный субстрат для тарифов:

| Тариф            | Что открывает                                                        |
| ---------------- | ------------------------------------------------------------------- |
| Free             | публичные fns-пакеты, наши base-fn, одна организация, лимит compute/storage |
| Paid             | приватные пакеты, право publish, кастомные домены, больше storage (строк графа), больше service-слотов/compute, egress-allowlist, сторонние impl-пакеты (mixed), SSO для организаций |
| Self-hosted/Mixed| оплата за объём хранения графа у нас + storage API + egress         |

Реестр пакетов — естественная точка paywall (gate на publish/install приватных
и премиум-пакетов). Смешанный режим (bring-your-own-executor) — сам по себе
платная фича. Это **не убивает проект**, а наоборот — даёт несколько ортогональных
рычагов монетизации, не ломая бесплатный self-hosted путь.

## 7. Риски и нестыковки (то, что ты просил подсветить)

| #      | Риск / нестыковка                                                                                                                              |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **R1** | **Гейтинга эффектов нет.** «Пакеты без impl» ≠ безопасность. Облачный юзер композит существующих эффектных base-fn. Надо строить рантайм-гейт. Без него вся облачная модель безопасности — фикция. |
| **R2** | `:terminal` и `:list-append` **задокументированы как реальные, но не реализованы** (ни поля, ни энфорсмента). Кейс ограниченного редактирования зависит от них. |
| **R3** | **Нет round-trip экспортёра** граф→EDN. И publish, и export его требуют. |
| **R4** | `impl-hash` — заглушка `nil`. Детекция breaking-change между версиями пакета слепа. |
| **R5** | `org-id` на каждой таблице — **в напряжении с принципом #2** (минимум полей). Нужен ADR. |
| **R6** | **Чтение сегодня полностью анонимно** — каждый read-эндпоинт открыт. Мультитенант → КАЖДЫЙ read-путь должен стать org-scoped. Поверхность огромна и хрупка → RLS обязателен как нижний предохранитель. |
| **R7** | Смешанный режим: наш storage API при баге не должен отдать чужие данные → API тоже под RLS, не только app-проверки. Их executor исполняет их эффекты — это их зона; наша зона — только скоуп storage API. |
| **R8** | LRU-кэш per-branch хендлеров (`max 16`) **протечёт между организациями**, если не сделать его per-org. Конкретный баг. |
| **R9** | Vault/секреты **глобальны** — все аутентифицированные видят все. Нужен org/user-скоуп путей секретов; сегодня его нет. |
| **R10**| Проверка владения доменом — сетевой **эффект**, запрещённый облачным юзерам. Значит fn-проверки — привилегированная платформенная, не пользовательская. Ломает наивное «через граф». |
| **R11**| Два разных роутинга смешиваются: поддомен организации → тенант (editor/API) и hostname развёрнутого веб-сервера → `:service`. Это разные отображения. |
| **R12**| **Уникальность имён** сегодня `UNIQUE(namespace-id, name)` + глобально-в-батче (валидатор). Мультитенант → sync-валидатор должен скоупиться per-org, иначе две организации не смогут иметь fn с одинаковым именем даже в своих неймспейсах. |
| **R-NS**| **M2M для неймспейсов не реализован** (вопреки памяти — `fn.namespace-id` единственный FK, `:ns` — дерево). Это упрощает упаковку, но твой interface-gathering кейс потребует НОВОЙ сущности (нарушает #2) и сейчас не существует. |
| **R13**| Замена `AUTH_TOKEN` (общий пароль) на per-user — крупная переделка auth (таблица user + сессии/JWT + проброс контекста). Нельзя недооценивать объём. |

## 8. Последовательность реализации (предлагаемая)

- **Фаза 0 (подготовка):** ADR по `org-id` vs принцип #2 (R5); подтвердить
  модель неймспейсов (R-NS); решить порядок — гейт эффектов (R1) можно начать
  параллельно, т.к. он самостоятелен.
- **Фаза 1 (пакеты):** round-trip экспортёр (R3) → реальный `impl-hash` (R4) →
  версионные констрейнты зависимостей → реестр + publish/install → расщепление
  каналов impl/fns → `executor-packages.edn` манифест → вынос доменных пакетов
  из ядра (§2.9).
- **Фаза 1.5 (гейт эффектов, R1):** `:allowed-effects` в ctx + проверка в
  `record-effect!` + билд-тайм фильтрация реестра. Предусловие облака.
- **Фаза 2 (организации):** `org-id` + `OrgScopedStorage` + RLS (R6) →
  per-org LRU (R8) → поддомены/кастомные домены (R10, R11) → org-скоуп секретов
  (R9).
- **Фаза 3 (пользователи/права):** auth-переделка (R13) → `grant`-примитив →
  `:terminal`/`:list-append` (R2) → личные неймспейсы → workspaces.
- **Фаза 4 (распил/смешанный режим):** протоколы + deps.edn git-deps; смешанный
  режим как композиция фаз 2+4. Polylith — опционально, не блокер.

> Если делать строго последовательно — **фаза 1 (пакеты) полностью автономна** и
> даёт ценность сама по себе. Фазы 2–4 фиксируются этим документом как план.
