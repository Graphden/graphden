# graphden-fn-refactor — декомпозиция impl в атомарные base-fn + fn-def

Задача скилла: систематически чинить нарушение базового принципа Graphden —
**пользователь Graphden'а пишет fn-def'ы, не base-fn'ы**. Всё, что
пользователю может понадобиться варьировать без обращения к админу за
новым Clojure-impl'ом, должно быть видно как граф fn-def, а не спрятано
в `defbase`. Узкий список того, что обоснованно остаётся `defbase`'ом
— в §3 ниже; критерий — user-composability test.

Любая многошаговая обработка — это *композиция*. Композиция должна
быть в `fns.edn`, а не в `impls.clj`.

`web/crud` и `app/layout` по этому методу уже декомпозированы (этапы L1–L2,
C1–C4) — готовые примеры смотри в их `fns.edn`. Метод ниже — общий, для
любой следующей цели.

## 1. Что считается нарушением

Нарушение — `defbase`, у которого:

- **(a) большое тело** — > ~5 строк реальной логики (без учёта input-validation);
- **(b) вызов другой base-fn** — скрытая композиция A→B, которой место в графе;
- **(c) делегирование в крупную рукописную функцию** — `defbase` тонкий, но
  зовёт `helper/process-foo` из соседнего `src/`-неймспейса, где живёт
  многошаговый pipeline. Тонкая обёртка не спасает: композиция всё равно
  спрятана в коде, а не в графе (нарушает принцип #3 — explicit over implicit).

Тип **(c)** — самый частый и коварный: `impls.clj` выглядит тонким шимом, а
весь pipeline (`parse → validate → write → respond`, `parse → load → compute`)
сидит в `src/`.

## 2. Сначала: жива ли цель?

**Перед декомпозицией убедись, что цель вообще исполняется.** Тонкий `defbase`
может делегировать в мёртвый `src/`-pipeline, у которого нет ни одного
вызывающего. Декомпозировать мёртвый код в N граф-fn-def'ов — хуже, чем
бесполезно: добавляешь сущности под код, который никогда не запускается
(нарушает #2 и #6).

Проверь:

- fn достижима от корня приложения (`web-server`) / startup-fn / маршрута?
- маршрут, который она обслуживает, реально дёргают — editor JS его зовёт,
  `curl` отдаёт осмысленный ответ, DOM-хуки (`#modal-content`, кастомные
  события) в editor JS существуют?

Если цель мертва → **удаляй весь кластер** (impl + fn-def + маршрут + handler),
не декомпозируй. Реальный кейс: серверный рендеринг `/partials/entity-*` —
остаток до-cytoscape htmx-редактора; попытка декомпозиции вскрыла, что он
мёртв (editor JS его не зовёт, `parse-uri-segments` не знает его путей) →
удалено ~430 строк вместо «распиливания мертвечины».

Систематический поиск мёртвого кода — см. §9 (reachability-аудит).

## 3. Критерий «можно оставить base-fn'ом» — user-composability test

Главный тест перед тем, как защитить любую `defbase` от декомпозиции:

> **Может ли наш пользователь (НЕ-админ, пишущий fn-def'ы) поменять
> поведение этой fn, варьируя композицию в графе — без помощи админа,
> добавляющего новый Clojure-impl?**

Если ОТВЕТ «нет, придётся писать base-fn» — она по определению скрывает
композицию, которой место в графе. Это нарушение принципа #3 (explicit
over implicit) и заодно ломает обещание Graphden'а — *«код = граф в БД»*
без необходимости в Clojure-разработчике на каждое микро-изменение.

**Любая многошаговая обработка — это композиция.** Композиция должна
быть в `fns.edn`, а не в `impls.clj`. Точка.

Узкий список тех `defbase`, что ОБОСНОВАННО остаются Clojure-impl'ом:

### 3.1. ONE прямой library / Java / `clojure.core` вызов + boundary-coercion

Тело — это ровно `(lib/something arg ...)`, плюс ОДНА минимальная shape-coercion
строго на границе с библиотекой (graphden-форма → library-форма).

Coercion ОК:

- `vec` под seq-аргумент библиотеки, которая ждёт vector
- `(keyword key)` где библиотека ждёт keyword, а JSONB-roundtrip отдал string
- `(constantly response)` где библиотека ждёт `(fn [req] resp)`

Coercion НЕ ОК (это уже композиция, режется):

- Любая ветвь `cond` / `case` / `when-let` по доменной логике
- Сборка структуры из нескольких частей (`{:status ... :body ...}` собранный
  из вычисленных аргументов = композиция, не coercion)
- Литералы предметной области, прибитые в код (`[:meta {:charset "utf-8"}]`,
  `"<p class='error'>"`, hardcoded status 400)

Тест на coercion: **если бы пользователь подал данные уже в нужной библиотеке
форме — тело сократилось бы до одной строки `(lib/fn …)`**? Тогда обёртка
честная. Если бы пользователю всё равно пришлось бы добавить ту же ветку
руками — значит ветка предметная, режь.

Примеры честных library-обёрток: `render-hiccup` (`(str (h/html hiccup))`),
`ring-router-fn` (`(reitit/router (coerce routes))`), `ring-handler-fn`,
`pg-query`, `sha256-hex-fn`, `str-split-fn`, `sleep-fn`.

### 3.2. Executor-ядро

Примитивы исполнителя, которыми пользуется ВЕСЬ остальной граф и которые
по определению нельзя выразить через граф (потому что граф собирается ИЗ
них):

- Управление потоком: `cond` / `case` / `if` / `try` / `and` / `or`
- Concurrency-ядро: `future` / `loop-until-interrupted` / `sleep` /
  `sleep-until-ms` / `cron-next-after`
- Состояние: `atom` / `swap-conj` / `deref`
- Сравнение / структурные: `=` / `nil?` / `some?` / `get` / `assoc`

Это аналог тех самых ~10 функций clojure.core, на которых стоит всё
остальное. Их не декомпозируют — они И ЕСТЬ дно.

### 3.3. Алгоритм с инвариантом, который нельзя разложить

Узкий список:

- **Journalled-txn с rollback** — body + on-throw-rollback ОДНОГО `:try`
  должны видеть ОДИН и тот же `journal` атом. Это `apply-update-record-
  type-body`'s shape: body — внутри `:try`, rollback — в `:on-throw`,
  оба читают журнал. Фазы ВНУТРИ body — это helper'ы (имена + код-обзорность),
  но граница `:try` — индивизибельна.
- **Cycle-guarded recursion** — `letfn` со взаимной рекурсией + cycle-set,
  как `layout.graph/build-graph-elements`. Cycle-set должен переживать
  все рекурсивные вызовы как один shared state; разнести на отдельные
  base-fn'ы нельзя.

Заметь: это НЕ список «всё что выглядит как один алгоритм», это закрытый
список ВИДОВ инвариантов. Если ты подгоняешь под «один алгоритм» что-то
другое — ты применяешь старый параграф 3 заново.

### 3.4. Чего в этом списке НЕТ (и почему я раньше там был не прав)

- ❌ «Library-adapter boilerplate» — это была лазейка. `html-page` собирает
  hardcoded `[:html [:head [:meta charset=utf-8] ...] [:body ...]]` — это
  не boundary, это шаблон страницы, и пользователь должен мочь его варьировать.
  Декомпозируется на `:hiccup-element` (атомарный primitive) + граф-сборку.
- ❌ «Сборка ответа» (`_rejection-response`, error-builder'ы) — литералы
  `{:status 400 :body "<p class=error>...</p>"}` это композиция ответа,
  не coercion. Декомпозируется на `:ring-response` + `:str-concat` + `:get`.
- ❌ «Декомпозиция была бы _step1/_step2 без смысла» — если ШВЫ не именуются,
  то либо это пункт 3.1 / 3.2 / 3.3 (тогда оставляй), либо ты неправильно
  ищешь швы. Швы есть — `parse / load / validate / transform / write /
  format / respond` всегда дают имена. Если в твоей `defbase` НЕТ ни одного
  из этих — это уже подозрительно, скорее всего перекошенная декомпозиция.

### 3.5. Что делать если новых атомарных primitive'ов не хватает

При декомпозиции часто оказывается, что граф-композиция требует базового
кирпичика, которого ещё нет — например `:hiccup-element` (тег + attrs +
children), `:str-concat`, `:ring-response-builder`. Это **нормально и
ожидаемо**. Поэтапная декомпозиция (§4):

1. Распиливаешь большую base-fn на несколько поменьше + fn-def-скреп.
2. На след. этапе ВНУТРИ скрепа находишь следующий слой композиции,
   который нужно расписать в граф — и оказывается, что нужен новый
   атомарный primitive.
3. Добавляешь его как минимальную base-fn по правилу 3.1 (ONE library call)
   или 3.2 (executor-примитив).
4. Дальше скреп переписывается через новый primitive — `defbase` промежуточного
   слоя исчезает.

Это и есть «итерация до идеальной чистоты»: каждый раз сводим всё к
{пользовательской композиции в графе} + {минимальный словарь base-fn по
правилам 3.1–3.3}.

## 4. Метод: одна декомпозиция = один этап

**Не пытайся за один заход распилить большую impl до атома.** Действуй
поэтапно: на каждом этапе одна большая impl → несколько ПО-МЕНЬШЕ + один
fn-def-«скреп». Получившиеся base-fn ещё не атомарны — это нормально,
следующий этап режет их дальше.

### Рецепт одного этапа

1. **Выбери цель** — одну base-fn с нарушением (a/b/c). Проверь §2 (жива?).
2. **Найди швы** — раздели тело на семантические шаги: `parse` / `load` /
   `validate` / `transform` / `write` / `format`. Каждый шаг, который можно
   назвать, — кандидат в отдельную base-fn.
3. **Создай меньшие base-fn** — для каждого шва `_`-приватная base-fn
   (`graphden-fn-design` §1). Шаг-«один алгоритм» — допустимо крупная base-fn,
   режется позже.
4. **Напиши fn-def-скреп** в `fns.edn` — он КОМПОНУЕТ новые base-fn и
   воспроизводит исходное поведение.
5. **Замени оригинал** — fn-def забирает ИМЯ старой base-fn; старый `defbase`
   и его строка в map'е `impls` удаляются. Имя сохраняется → все ссылки целы.
6. **Объяви типы** новых base-fn в `fns.edn` (см. §6).
7. **Проверь** эквивалентность (REPL/живой эндпоинт), затем ОДИН `bb rebuild`
   → `bb verify` → smoke.
8. **Следующий этап** — режь одну из новых base-fn дальше.

### Канонический паттерн: handler = parse → validate → apply

Request-handler `defbase` почти всегда режется на три стадии, склеенные `:if`
или `:cond` (так сделаны C2–C4 в `web/crud`):

- `_parse-*` (base-fn) — разбирает Ring-запрос → бандл данных.
- `_validate-*` (base-fn) — гварды → **сам rejection-ответ** (или nil).
  Возвращая готовую форму ответа, а не абстрактный «вердикт», ты позволяешь
  `:if`-у переиспользовать ref валидации как ветку `:then` — отдельный
  builder ответа не нужен.
- `_apply-*` (base-fn) — нерезаемое императивное ядро (DB-запись и т.п.) →
  success-ответ.
- Скреп:

  ```clojure
  {:name :process-foo
   :parent :if
   :args {:test :_rejected?              ; (some? validation)
          :then :_validate-foo            ; rejection-ответ = сам результат валидации
          :else :_apply-foo
          :validation :_validate-foo      ; общий под-результат, кэшируется
          :parsed :_parse-foo}}
  ```

  `:cond` вместо `:if` — когда у гвардов разные статические сообщения (каждый
  гвард = клауза `[predicate error-response]`, `:else` = apply). `:if`/`:cond`
  **ленивы** — запись (`_apply-*`) исполняется ТОЛЬКО когда валидация прошла.
- Тесты: перенацель существующие поведенческие тесты на локальный хелпер,
  воспроизводящий `parse→validate→apply` (тест-аналог графа).

### fn-def-скреп vs `src/`-helper — что выбрать для шва

- Шаг — pipeline чистых трансформаций значения → **fn-def-скреп** (видно в графе). ⬅ цель.
- Шаг — stateful-рекурсия / mutable-аккумулятор / транзакция с rollback →
  оставь в `src/` за ОДНОЙ base-fn (`_apply-*`).

## 5. ctx-threading

`defbase` неявно получает символ `ctx` (storage, graph-cache). ctx-зависимый
шаг становится обычной base-fn, читающей `ctx` в теле — и спокойно компонуется
в fn-def. Пример: `_load-graph-cached []` — 0-арная base-fn, тело
`(load-graph-entities ctx)`; в fn-def привязывается ref-биндингом без аргументов.

## 6. Типы, sync и JSONB-roundtrip

Graphden type-проверяет ВСЕ fn-def при sync (топологический порядок).
Для новых base-fn в `fns.edn`:

- `:args {:x {:type T :description "…"}}` — тип каждого слота; `:return-type T`.
- Слот, принимающий ГОТОВОЕ значение от base-fn-ref (не callable) → НЕ `:any`:
  `:any` = «не трогать», executor не сделает force-deref delay'я. Бери `:jsonb`
  (или конкретный record). `:any` — только для уже-готовой Clojure-fn,
  `:fn` — для fn-graph под HOF-wrap.
- Имя проверяется на ГЛОБАЛЬНУЮ уникальность, включая `_`-приватные — грепни
  `:name :foo` / `defbase foo` по `resources/packages/` перед именованием.

**Гоча: JSONB-roundtrip кейвордит ключи, но строкует вложенные keyword-значения.**
Литералы в `:value` / `:args` fn-def хранятся как JSONB. На чтении ключи мап
кейвордятся, а keyword-ЗНАЧЕНИЯ внутри векторов/мап возвращаются СТРОКАМИ:
`[:p {:class "x"}]` → `["p" {:class "x"}]`, `[["ID" :id]]` → `[["ID" "id"]]`.
Следствия:

- `:const` с сырым hiccup ломается (тег `:p` → `"p"`, hiccup2 ждёт keyword) —
  строй hiccup через base-fn `:hiccup` (она кейвордит тег);
- base-fn, потребляющая keyword-данные из JSONB-источника, должна кейвордить
  на границе (`(keyword key-raw)`).

## 7. Workflow

Отлаживай в живом nREPL (скилл `graphden-repl`), `bb rebuild` — один раз в конце,
затем `bb verify` (per-section ✓/✗) → smoke эндпоинта → `bb ci`.

Декларативный sync **не удаляет** строки, выпавшие из `fns.edn` — они копятся
в dev-БД. Удалил fn-def → для чистого состояния (и достоверного
reachability-аудита) нужен `bb deploy` (truncate + чистый sync), не `bb rebuild`.

Коммить по-этапно (чекпойнт на этап) — но только когда пользователь попросит.

## 8. Анти-паттерны

- **Декомпозиция мёртвого кода.** Распилить цель, у которой нет вызывающих —
  +N сущностей под неисполняемый код. Сначала §2.
- **Big-bang.** Распилить 1400-строчный неймспейс за один заход — гарантия
  регрессий. Только по-этапно, с проверкой каждого этапа.
- **«Не вижу швов» как отговорка от декомпозиции.** Если ты не нашёл
  именуемых швов (`parse` / `load` / `validate` / `transform` / `write` /
  `format` / `respond`) — это не значит, что их нет, и точно не основание
  не пилить. Это значит: либо цель действительно из узкого списка §3.1–3.3
  (тогда оставь явно по этому правилу, а не «потому что один алгоритм»),
  либо ты смотришь не под тем углом — попробуй декомпозировать по доменным
  концепциям ответа / запроса, а не по строкам кода.
- **Дробление на `_step1/_step2/_step3` без семантических имён —
  обфускация, не декомпозиция.** Если имя честно сводится к «первый шаг
  что-то делает, второй продолжает» — это не швы. Либо ищи доменные имена,
  либо это §3.1–3.3 (по правилу, не по ощущению).
- **base-fn зовёт base-fn в новом коде.** Если шаг A нуждается в шаге B —
  это ребро графа (fn-def-скреп), не вызов в Clojure.
- **«Удобная» обёртка >1 вызова.** Новая base-fn вокруг `parse + validate` —
  то же нарушение (a), просто меньшего размера.
- **Молчаливый откат при блокере.** Если шов оказался нерезаемым или цель
  оказалась мёртвой — озвучь находку и переиграй план, не откатывай тихо.
- **Коммит без спроса.**

## 9. Reachability-аудит — поиск мёртвого кода

Чтобы найти неиспользуемые fn-def'ы по всему графу:

1. `bb deploy` — чистая БД (иначе накопленный мусор исказит результат).
2. `curl /api/graph/entities` — дамп `fns` / `slots` / `fn-slots` / `bindings`
   / `list-items`.
3. Построй граф рёбер fn→fn: `parent-ids`; `base-fn-id` / `element-fn-id` /
   `return-type-fn-id`; тип каждого собственного слота (`fn-slot`→`slot`→
   `type-fn-id`); биндинги fn (`ref-fn-id`, `type-override-fn-id`) и их
   `binding-list-item.ref-fn-id`. Это ПОЛНЫЙ набор механизмов ссылки.
4. BFS от корней: `web-server` + все fn пакета `examples`.
5. Недостижимые **именованные composed fn-def** — кандидаты в мёртвый код
   (как был `/partials`-рендеринг). Недостижимые **base-fn и type-row** — это
   словарь языка (примитивы `div`/`first`, типы `uuid`/`percent`); приложение
   использует подмножество — НЕ мёртвый код.
6. Для подозрительных грепни имя по `resources/` — отсей совпадения в
   комментариях/описаниях/подстроках, прежде чем удалять.
